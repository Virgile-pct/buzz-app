Buzz federated identity module implementation specification
Draft for Brad Seiler · 9 October 2026 · Target: block/buzz-app
Implement one host-owned federated identity module that signs a user in once, keeps the resulting session credential in OS secure storage, obtains community-specific NIP-FI assertions, and authenticates approved plugin requests. The Builderlab plugin and Builderlab CLI consume this module without receiving the upstream session credential.
The governing proposal is Builderlab Client Login — Login Eng Design. Brad's accepted correction adopts Will Pfleger's recommendation: use the provider-neutral NIP-FA adapter contract in place of the proposal's Builderlab-specific login, exchange, and assertion routes. NIP-FA defines client-to-adapter operations; NIP-FI defines assertion verification and relay transport. SDK names, plugin authorization, storage scope, lifecycle rules, and the CLI bridge below remain proposed implementation decisions.
1. Outcome and scope
A user signs in from a protected community or Builderlab settings. The same session then serves relay authorization, hosted-community management, remote-agent operations, and a configured local bl process. Restarting Buzz restores the session without another browser handoff while the session remains valid. Ordinary Nostr communities continue to work without a federated login.
This specification covers packaged desktop, including native transport and the shared frontend SDK. macOS is the first attended acceptance target; Windows and Linux use the existing OS credential adapters and require their own acceptance evidence. The Node browser host remains a development/test host; it is not a production credential broker. Preserve its existing supported flows, but do not claim new browser FI support or add browser token storage to obtain parity.
The work does not implement an IdP, relay authorization policy, SCIM, identity rotation/recovery, nsec backup, a plugin sandbox, or remote/headless CLI brokerage. The local CLI integration requires a running Buzz desktop. A separate CLI change is necessary for the full proposal; the app module can ship independently with CLI setup unavailable until that client contract exists.

Use one native session owner per configured authority, composed at application startup. Plugin disposal removes that plugin's access and pending work, not the shared login. The existing IdentityHost continues to own the Nostr private key. Relay transport owns sending assertions; plugins never receive them.
Introduce a validated, versioned, nonsecret build descriptor, for example BUZZ_BUILD_FEDERATED_IDENTITY_CONFIG. Version 1 contains one configured authority per build; the data shape need not hardcode Builderlab, and an unconfigured OSS build remains supported. Do not add runtime issuer discovery or a general OAuth-provider framework.

The adapter contract is:
Operation	Route relative to adapterBase	Wire contract
Browser login	GET /v1/login/start	return_to, handoff_challenge, handoff_challenge_method=S256
Code exchange	POST /v1/login/exchange	JSON {code, handoff_secret}; returns session_token and RFC 3339 expires_at
Session verification/restore	GET /v1/session	Authorization: Bearer <session_token>; returns the fixed session expiry and optional private account display fields
Relay assertion	POST /v1/identity/assertions	Bearer session in Authorization, NIP-98 proof in Nostr-Authorization; exact JSON contract in section 6
Append these suffixes to the configured base path without discarding its prefix. Do not retain type=cli, product=builderlab, legacy OAuth field names, session_credential, or X-BB-Session-Credential as the standard adapter contract. NIP-FA defines no logout route or required stable account subject. Local sign-out is required; server revocation requires a separately documented extension.
The requested same-origin Builderlab API proxy has a protocol dependency: the pinned NIP-FA text permits session tokens only on its defined adapter endpoints. Will's separate document comment proposes allowing the adapter's origin. Preserve the intended single-session proxy design, but require that specification change and a documented same-origin API authentication contract before enabling generic plugin/CLI forwarding. Do not treat backend acceptance of a token as protocol permission, silently fall back to the legacy header, or claim this extension is already standardized.
Validation requirements:
Native build validation is authoritative; frontend receives only its public projection. The adapter base and derived URLs require HTTPS, the exact configured identity origin, and no embedded credentials, queries, or fragments. Validate any base-path prefix and its joining semantics. Callers cannot override the base, derived routes, callback, or handoff values.
Canonicalize hostnames with the URL parser. For version 1, *.communities.buzz.xyz matches one nonempty leftmost label, excludes the apex and deeper names, and requires port 443. Exact host entries can declare an explicit port. Match DNS labels, never string substrings; reject wildcard placement elsewhere and ambiguous entries.
Canonicalize the selected relay as NIP-FA's wss://host[:port]: lowercase ASCII DNS without a trailing dot, canonical IP literals, no default port, trailing slash, path, query, or fragment; reject port 80. Its required JWT audience is https:// plus that same authority, preserving any nondefault port. The adapter must allow the exact canonical relay.
A wildcard selects the configured authority only after the relay's NIP-11 response explicitly indicates that federated identity is required. A matching hostname alone must not trigger assertion acquisition or attachment. The issuer and relay still enforce eligibility; NIP-11 must never select a credential destination.
Retire conflicting BUZZ_BUILDERLAB_URL and BUZZ_BUILD_ENTERPRISE_AUTH_* inputs as callers migrate. During transition, reject conflicting values rather than choosing precedence silently. Release packaging must be updated with the same change.
4. SDK and plugin authorization
Expose an injected federatedIdentity service in the same Cordis/authoring pattern as host. Suggested public contract:
ts
interface FederatedIdentity {
  snapshot(): SessionSnapshot;
  subscribe(listener: () => void): () => void;
  signIn(): Promise<SessionSnapshot>;
  cancelSignIn(): Promise<void>;
  signOut(): Promise<void>;
  request(input: AuthenticatedRequest): Promise<HostResponse>;
}
interface AuthenticatedRequest {
  path: string;
  method?: "GET" | "HEAD" | "POST" | "PUT" | "PATCH" | "DELETE";
  headers?: Readonly<Record<string, string>>;
  body?: string;
}
Copy code block
SessionSnapshot contains a status, public configured authority, verified subject/display email when available, a nonsensitive session revision, and a sanitized failure code. Statuses distinguish unconfigured, signed-out, signing-in, restoring, signed-in, reauthentication-required, and unavailable. Storage/network unavailability is not evidence that the user has no account. Snapshots never contain a credential, assertion, code, verifier, local CLI token, or authorization header.
The native-only interface supplies assertionForRelay(relay, viewer) to transport; obtaining a JWT is a module capability, not a raw-token plugin API. Do not add a token getter as an implementation shortcut.
For the source document's open authorization question, use explicit native plugin grants. Extend the existing manifest/manager contract with an authenticated authority grant and allowed method/path operations. Derive effective grants for bundled block.builderlab and block.hosted-communities from the compiled descriptor. External plugins receive no FI grant merely by declaring an ordinary networkOrigins entry; any future FI grant must appear in the existing installation/update access review.
Every request checks the enabled current plugin revision and its live registration. Revocation, replacement, or failed activation invalidates pending results and CLI registrations. Caller-supplied plugin IDs are not an adversarial security boundary in the current trusted WebView model. Strong isolation would require separate execution principals and is a separate project.
Proxy rules:
Accept only canonical relative API paths within apiBasePath; reject absolute URLs, scheme-relative URLs, fragments, backslashes, encoded separators, and traversal before resolving. The resolved destination must still equal the configured identity origin.
Require an explicit permitted method/path operation. Start with the existing Builderlab agent and hosted-community routes. Add CLI capability/resource routes with the companion CLI contract; do not grant every route under the domain by default.
Reserve all standard adapter routes and any configured revocation extension to the module. Proxy consumers cannot use those routes to obtain credentials or bypass lifecycle handling.
Reject caller Authorization, Nostr-Authorization, X-BB-Session-Credential, Cookie, Host, proxy, hop-by-hop, and content-length headers case-insensitively. Once the same-origin extension described in section 3 is agreed and supported, native code injects exactly one session header according to that API contract after destination/grant validation. Adapter operations always use Authorization: Bearer; the local CLI token is never forwarded upstream.
Reuse host transport bounds: 1 MiB UTF-8 request body, 8 KiB request headers, 16 MiB UTF-8 response body, 16 KiB response headers, and a 30-second total deadline. Follow no redirects. Strip cookies and credential-bearing response headers; treat authentication response bodies as native-only. Binary/streaming CLI APIs require an explicit bounded extension before being advertised.
Capture session revision and plugin registration before I/O; recheck before releasing a result. Abort where possible, discard stale results, and never automatically repeat a state-changing request after authentication failure or uncertain delivery.
5. Login, persistence, and sign-out
Reuse the callback owner, with all FI-specific secrets and exchange I/O in Rust. Starting login requires an explicit user action. Concurrent consumers share one authority login attempt and observe its state; they do not open multiple browsers. Coordinate with other users of the existing single callback listener rather than replacing their pending attempt.
Native code generates a high-entropy handoff secret and opens /v1/login/start with return_to, handoff_challenge=base64url(sha256(handoff_secret)), and handoff_challenge_method=S256. The callback uses HTTP on exactly 127.0.0.1 or [::1], on an ephemeral port; reject localhost and other loopback addresses. Adapt the existing callback owner to this contract instead of requiring an undocumented echoed OAuth state parameter. Bind callbacks to the active attempt, and exchange one bounded single-use code with the native handoff secret at /v1/login/exchange.
Parse session_token and RFC 3339 expires_at, then call /v1/session with exactly one Authorization: Bearer <session_token>. Compare exchange and session-check expiry as instants and reject unequal, invalid, or expired values. Persist only after successful verification. Optional email and profile_projection are private display data; their absence must not fail login. Browser navigation may follow IdP redirects; native exchange, session check, and assertion calls follow none. A canceled, superseded, signed-out, or identity-retired attempt cannot install a late credential.
Store one versioned session record per application profile, canonical identity authority/configuration fingerprint, and debug/release namespace. Store fixed expiry, optional verified display data, and an opaque record revision alongside the secret in the secure record. Do not require an account subject from NIP-FA, or derive one from email or decoded assertion claims. Do not include the Nostr pubkey in the session's account key: relay assertions bind the active key separately, while one account session serves all callers. Only one account per authority/profile is active in this version.
Use the existing OS-store boundary; add serialized replacement and compare-delete for session records where needed. Never change human-key create-only semantics. A denied, locked, corrupt, or unavailable store fails explicitly without a plaintext fallback or replacement login overwriting unknown state. First use after launch validates a restored session through /v1/session and checks that its fixed expiry agrees with the stored session; concurrent consumers share that restore. No polling credential reader or second plugin cache is needed.
On sign-out, retire the in-memory session revision immediately, cancel outstanding acquisition, close affected protected sockets, revoke local CLI access, and clear assertion caches. Delete only the matching local record. NIP-FA alone provides local sign-out, not server session revocation; do not invent /v1/logout or send the adapter token to the former Builderlab logout route. If a separately agreed revocation extension exists, attempt it without allowing failure to prevent local removal, and accurately report whether revocation was confirmed. A failed local deletion remains a visible incomplete sign-out and must not silently restore on restart: retain a durable nonsensitive refusal marker for that record revision until deletion succeeds. Check it before restoration.
Distinguish signing out of the authority from deleting the Nostr identity. Authority sign-out preserves the Nostr key and ordinary communities. Integrate with the existing Buzz sign-out/wipe owner so deleting the human identity cannot leave FI sessions or CLI grants usable. App quit clears in-memory secrets and the local listener but retains the secure session for next launch. Disabling one plugin does not sign other consumers out.
This replaces plugin-memory session ownership and, for the Buzz-managed CLI mode, the earlier shared-Keychain approach: bl gets a local proxy token, not the upstream credential. Do not automatically import, overwrite, or delete an existing standalone CLI credential. Existing unmerged login work may supply useful code, but must be reconciled against this ownership model rather than treated as a required stack.
6. Relay assertion and transport contract
Use POST {adapterBase}/v1/identity/assertions. The previously inspected Builderlab /v1/buzz/identity/assertions action is legacy implementation evidence, not the target client contract. Native code sends the exact JSON bytes:
json
{"nostr_pubkey":"<active lowercase hex key>","relay_url":"<canonical wss URL>"}
Copy code block
Attach exactly one Authorization: Bearer <session_token> and one Nostr-Authorization: Nostr <base64-event>. The NIP-98 kind-27235 proof is signed by IdentityHost and has exactly one endpoint u, method=POST, and lowercase SHA-256 payload tag binding the exact body. Its timestamp is at most 60 seconds old and 5 seconds in the future. Limit the body to 4096 bytes, send no content encoding or unknown fields, and follow no redirects. Never accept a plugin-supplied pubkey/proof pair or attach auth_tag; this contract covers human keys.
The response is { assertion, nostr_pubkey, expires_at }, with assertion expires_at in Unix seconds, unlike session expiry. Bound and parse it natively; require the expected key, typ=nip-fi+jwt, the audience from section 3, and consistent future expiry no later than the session expiry, with exp - iat <= 300 seconds. JWT decoding is a local misuse check, not a substitute for relay signature verification. A rejected or unparseable success response is a refusal: keep the session, show the error, and do not retry automatically. These requirements come from the pinned NIP-FA contract; deployed adapter compatibility remains an acceptance gate.
Cache assertions only in native memory, scoped by authority configuration, session revision, active Nostr key, and exact community. Collapse concurrent acquisition for the same tuple. Never share an assertion across wildcard matches. Reuse only before expiry with a small explicit refresh margin; if a freshly minted token has less lifetime than that margin, permit its still-valid lifetime without entering an immediate refresh loop. Retirement of any tuple component discards outstanding results and cached tokens.
Native relay assertion acquisition and attachment require an NIP-11 response from that relay with limitation.federated_identity explicitly set to true. This is the governing requirement, including for a hostname matching the compiled community mapping. The mapping selects the trusted authority; it does not independently require FI.
A valid NIP-11 response with the flag absent or false uses the existing Nostr authentication path without acquiring or attaching a federated assertion, even if one is cached from an earlier connection.
A response requiring FI must also pass the supported FI descriptor checks and match a configured authority. Otherwise report an actionable unsupported/configuration error and send no assertion; do not connect through a non-FI fallback.
Failed, malformed, or inconsistent discovery never authorizes sending a federated credential. Report the discovery error and allow retry; do not infer an FI requirement from the hostname or an available cached token.
Bind the discovery decision to the exact relay and connection generation. Re-evaluate on reconnect; a late discovery/acquisition result must not authorize a different relay or superseded connection. All native HTTP, WebSocket, media, and Git attachment paths consume this same decision.
Discovery requests carry no FI assertion. This condition applies to the relay access assertion, not to normal NIP-42, NIP-98, or Blossom possession proofs. The upstream session credential is sent only to the configured identity service and never to the relay. This rule incorporates Brad Seiler's 9 October clarification in the originating specification thread.
Transport must follow NIP-FI:
WebSocket upgrade: exactly one Nostr-Federated-Identity: Bearer <assertion> header, followed by existing NIP-42 possession proof from the same key. Standard renderer WebSocket cannot supply this header. Add a narrow native socket adapter using the existing native WebSocket dependency and inject it into the live transport. Keep event routing, subscriptions, retry budgets, and resubscription in the existing live.ts owner.
HTTP: attach the assertion beside the existing NIP-98 proof; do not replace Authorization. Cover query/event writes, admission/invites, workflows, agent reads, and other currently shipped protected HTTP routes.
Media: attach it beside the existing kind-24242 Blossom proof on upload, rendering, streaming/range, copy, and download paths. Keep the relay's media proof exception; do not replace working Blossom authentication with NIP-98.
Git: cover both the current native project reader and authorization helpers. The native subprocess needs both headers restricted to the exact repository origin, with redirects disabled and no headers in argv, persistent Git config, or logs. A single prefetch token is acceptable only while valid; an expired read may restart with fresh authorization, but no push/write is blindly replayed. Audit this separately from the generic HTTP helper.
Expiry: close a socket by assertion expiry and re-enter the existing connection lifecycle with fresh authorization. Reconnect must complete fresh NIP-42. The relay may close earlier under its configured maximum lifetime. Add no competing reconnect loop, and do not substitute query parameters, subprotocols, or event tags for the FI header.
The issuer enforces enrollment, product/workspace access, and binding. On binding_mismatch, direct the user to the existing identity-linking flow; never generate or silently bind a replacement key. Generalizing that linking UI for non-Builderlab operators is outside the module's v1 scope.
7. Failure behavior
Failure	Client behavior
Adapter 401 with session_required or session_expired, or known local session expiry	Retire only that session revision; block protected work and offer one explicit sign-in action. A stale failure cannot delete a newer session. An unknown 401 code does not clear the session.
Issuer authorization_denied or binding_mismatch	Retain the valid account login; clear the affected relay assertion and show access/linking guidance. Logging in again is not assumed to fix eligibility.
invalid_proof, malformed assertion, key/audience mismatch	Fail closed with a sanitized diagnostic; do not fall back or loop through login.
Adapter 429, any 5xx, timeout, or offline	Keep the session and retry adapter operations with bounded backoff, respecting Retry-After where supplied. Show failure after the bounded attempts. No browser launch from retry and no replay of state-changing plugin API calls.
Adapter invalid request, oversized request, unknown denial code/status, redirect, or rejected success response	Keep the session, show refusal, and do not retry automatically.
Relay evidence rejection	Discard the affected assertion; at most one fresh acquisition for a safely retryable connection/read. Preserve uncertain write status. Authorization denial must not trigger a refresh storm.
Proxy API 403	Surface the resource denial. Do not erase a session merely because one resource is forbidden.
Storage failure	Distinguish unavailable/denied/corrupt from absent; do not claim successful persistence or logout.
Plugin unload, user switch, sign-out, or configuration mismatch during I/O	Revoke local eligibility, cancel where possible, discard late results. Already-sent server mutations may still complete; retain existing operation receipts/idempotency handling.
Logs contain operation category, public destination identity, duration, and correlation identifiers where available. Do not log headers, JWTs, PKCE material, callback codes, response bodies from authentication, or session/local-token values. Do not put identity claims in Nostr profile metadata as part of this work.
8. Builderlab and CLI integration
Migrate Builderlab settings and remote-agent clients to federatedIdentity.request() and public session snapshots, subject to the same-origin protocol dependency in section 3. Keep agent creation, deletion, idempotency receipts, community enrollment, and NIP-OA behavior in their existing owners. Migrate native Hosted Communities to the same service, including its account display. Scope plugin account caches to session revision and any separately verified API account identifier, preserving existing community/key scoping; NIP-FA does not guarantee a subject or email.
The CLI portion is a versioned companion contract, not an existing CLI command. The inspected Builderlab CLI login implementation directly exchanges and verifies upstream credentials; that flow alone does not implement the proposed Buzz proxy.
Proposed local integration:
Builderlab plugin setup opts into a plugin-scoped native proxy registration. Native code binds an ephemeral 127.0.0.1 port and creates a cryptographically random 256-bit local bearer token. This listener is distinct from the short-lived browser callback listener.
The plugin initiates CLI configuration through a narrowly scoped native provisioning operation. Native code invokes a compatible bl configuration command and passes endpoint, protocol version, authority/profile, and local token over stdin. Do not pass tokens through shell arguments, renderer results, logs, or general plugin storage. The CLI stores the token in its secure store and only public routing metadata in its profile.
Proposed bridge wire format: POST /v1/request, exactly one Authorization: Bearer <local-token>, JSON containing the same relative path/method/headers/body contract as the SDK. Reply with a bounded {status, headers, body} upstream response or a structured bridge error. The bridge resolves the registered Builderlab plugin grant and calls the same FI proxy; it is not a second credential consumer.
Require the exact bound loopback Host, reject browser Origin requests and CORS/preflight, and accept no token in query parameters. Apply a 5-second bounded header read, the existing 30-second request deadline, and a small fixed concurrency limit (proposed: 8). The token scopes one profile, authority, plugin registration, and app instance; it grants no arbitrary host HTTP, signing, nsec export, or raw token operation.
Plugin disable/replacement, account change, sign-out, or app exit revokes the registration and token. On launch, if the integration was previously enabled, re-register and reconfigure the compatible CLI with a fresh token/port before marking it ready. Until then old CLI settings fail explicitly. Never reuse a port or token as evidence of authority.
Buzz-managed CLI mode must fail clearly when Buzz is closed, the plugin is inactive, or sign-in is required. It must not silently fall back to standalone credentials or launch another browser. Preserve a separately selected standalone CLI mode for use without Buzz.
The complete flow requires the companion CLI to route its real API call sites through this transport, including capability access and resource management. Verify endpoint and content-type coverage before calling that integration complete; streaming/binary operations cannot be assumed to fit the text proxy. No generic remote-agent credential delivery is added.

10. Acceptance and rollout
Use the lowest layer that proves each contract, with controlled clocks and deferred operations for races. Run full affected package suites at a recorded commit, repository-required checks, and attended native flows; fixture success does not prove native credential custody.
Contract	Required evidence
Build/routing	Unconfigured build; exact/wildcard positive and negative cases; wrong ports, encoded/trailing-host forms, conflicting config; NIP-11 explicitly requiring FI acquires/attaches only for a supported configured authority. Valid absent/false flags produce no acquisition or attachment, including with a matching hostname and cached assertion; failed/malformed/inconsistent discovery sends no FI credential. Reconnect and late-result tests prove relay/generation scoping. NIP-11 never selects the credential destination.

Roll out first with a configured staging build and disposable account/key. Before production, verify the deployed adapter base and all four NIP-FA routes, the actual key binding and exact canonical relay URL, and all shipped protected transport paths. Plugin/CLI proxy acceptance additionally requires the agreed same-origin protocol extension and evidence that the same session authorizes the required Builderlab APIs. Client wildcard routing does not replace the issuer's exact relay configuration.
Keep FI-required communities fail closed during rollback; remove the feature by withdrawing the affected build/configuration, not by retrying protected requests without assertions. Do not enable relay enforcement as part of this app implementation without coordinated deployment acceptance.
11. Decisions to ratify at implementation kickoff
The proposed defaults make the specification actionable without assuming the source document resolved its TBDs:
Plugin authority: native, revision-scoped explicit operation grants under the existing trusted-plugin model. Strong adversarial plugin isolation is not provided.
Session ownership: Buzz owns a separate secure session; Buzz-managed bl receives only a local proxy token. No automatic shared-CLI-Keychain migration.
Configuration scope: one authority per build initially, with a same-origin adapter base, standard NIP-FA route suffixes, and one-label community wildcards. Custom-domain communities require explicit entries. As directed by Brad, native relay assertion use requires the relay's NIP-11 response to indicate FI is required; a community mapping alone is insufficient. The NIP-FA route decision is accepted, not awaiting ratification.
Desktop/CLI scope: desktop first; the local CLI requires Buzz running and a companion CLI transport release. Existing standalone CLI mode remains a separate explicit choice.
Completion gate: one deployed session must authorize the required Buzz and Builderlab operations under an agreed same-origin extension to NIP-FA, and the proxy's bounded text contract must cover the agreed CLI operations. NIP-FA's current endpoint-only token restriction remains a tracked dependency; Will's endpoint recommendation does not itself amend that separate rule.
No source code was changed or application tests run in preparing this specification. The source review pins the app, issuer contract, and CLI references above; deployment compatibility and live acceptance remain implementation deliverables.
